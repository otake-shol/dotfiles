## 共通骨格

記事ごとに必要な節だけを選ぶ。

1. 読者が遭遇する状況、問題、従来手法の課題
2. 対象技術と問題の関係
3. 記事で扱う範囲と到達点
4. 前提概念または判断基準
5. 最小の例
6. 実践的な例と実行方法
7. 観察結果と意味
8. 制約、失敗条件、互換性、代替手段
9. まとめ
10. 参考資料

導入だけで対象読者、課題、到達点を判断できる状態にする。実験的な API やバージョン依存の機能には導入付近で警告を置く。

## 新しい API・機能の紹介

1. 対応状況と安定度
2. 現在の課題または従来のコード
3. 新機能の位置付け
4. 最小の使用例または差分
5. 仕様上の細かな挙動
6. 実際に動かす例
7. 制約とフォールバック
8. まとめと参考資料

仕様上の要件、ブラウザやランタイムの実装状況、手元の観測結果を混同しない。

## ハンズオン・実装チュートリアル

1. 技術の概要と完成形
2. 必要に応じた構成図
3. プロジェクト作成とインストール
4. ファイル単位の段階的な実装
5. 起動と操作のコマンド
6. 期待するログや画面
7. 応用機能または運用上の注意
8. まとめと参考資料

読者が新しい環境で再現できる粒度を保つ。省略したコードや設定がある場合は省略範囲を明記する。

## 調査・比較記事

1. 調査対象となる具体的な問題
2. 調査範囲、比較軸、検証環境、基準日
3. 判断に必要な標準や基礎概念
4. 対象ごとの観察
5. 共通点と相違点
6. 調査結果を反映した例
7. 実機または実行環境での検証結果
8. まとめと参考資料

比較軸を対象の調査後に都合よく変えない。未確認と非対応を区別する。

## 意見・経験記事

1. 現在の立場と経験の変化
2. テーマごとの実践と理由
3. 利点、限界、反論
4. 今後変わり得る点
5. まとめ

一人称と主観を使ってよい。個人の経験を一般的な事実として広げず、適用条件と反証可能性を残す。

## frontmatter の設計

対象媒体のスキーマを最優先する。スキーマが未定の場合だけ次を候補にする。

- `title`: 技術名と記事で行うことの組み合わせ
- `slug`: 英小文字の kebab-case
- `description` または `about`: 背景、技術の要点、到達点を結論込みで要約
- `createdAt` / `updatedAt`: タイムゾーンを含む日時
- `tags`: 広い分類と固有技術
- `thumbnail` / `image`: 内容がわかる代替テキストを併記
- `draft` または `published`: 初期状態を非公開に設定

理解度チェックを採用する媒体では記事の中心概念を問う選択式問題を置く。明らかな冗談を誤答にせず各選択肢に理由を付ける。問題数や YAML 形式を媒体のスキーマへ合わせる。

## 分量の参考値

元ガイドが 2025 年以降の公開記事 163 件から得た中央値をスコープ確認の参考値としてのみ使う。

| 項目 | 中央値・出現率 |
|---|---:|
| 本文 | 9,735 文字 |
| 本文の中央 50% | 6,660〜16,377 文字 |
| `##` 見出し | 6 個 |
| コードブロック | 9 個 |
| タイトル | 36 文字 |
| 概要 | 168 文字 |
| タグ | 2 個 |
| まとめ・参考資料 | 各 96.3% |
| コードブロック | 96.3% |
| 画像 | 77.9% |

数値へ記事を合わせない。短い API 紹介に節やコードを水増しせず、意見記事に不要な実装を追加しない。
