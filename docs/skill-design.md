# 自作スキルの設計規約

このリポジトリで管理する Agent Skills（Claude Code・Codex 共通）の作り方と改修の規約。新しいスキルを作るとき、既存スキルの手順や判断基準を変えるときに読む。

参考: 風音屋TechBlog「[AIエージェント向け業務手順書（Agent Skills）の設計方法](https://techblog.kazaneya.com/20261030-agent-skills/)」（2026-10-30）の考え方をこのリポジトリの構成に合わせて再構成した。確認日: 2026-11-05。

## 前提

AIの出力が期待とずれる主な原因は手順と判断基準を渡していないことにある。スキルは新しく入った人に渡す業務手順書と同じ役割を持つ。最初から完成させず、手直しが起きた箇所から育てる。

## 配置

| 対象 | 置き場所 |
| --- | --- |
| Claude Code・Codex で共有するスキル | `stow/agents/.agents/skills/<name>/` または用途別パッケージ（例: `stow/design/.agents/skills/<name>/`） |
| Claude Code から使う共有スキル | `stow/claude/.claude/skills/<name>` に相対パスの symlink |
| Claude Code 専用スキル | `stow/claude/.claude/skills/<name>/` |
| 個人情報を含むスキル | `~/.config/dotfiles-local/` に置き、symlink だけを作る（Git管理外） |

同じ手順を複数のスキルに書き写さない。共通の手順は別スキルや共通の参照資料に切り出し、参照先として名前を書く。

## ディレクトリの役割

必要になったものだけ作る。SKILL.md だけで足りるスキルに空のディレクトリを用意しない。

| パス | 役割 |
| --- | --- |
| `SKILL.md` | 入口。何をするか、いつ使うか、手順の概要、判断基準、参照先 |
| `references/` | 詳しい手順、仕様、判断基準の詳細、外部資料の要約。SKILL.md から必要なときだけ読ませる |
| `scripts/` | 答えが一つに決まる処理（計算、件数、判定、整形、検査） |
| `scripts/*.test.mjs` などのテスト | `scripts/` の回帰テスト。Node は `node:test`、Python は標準の `unittest` か pytest |
| `evals/` | 試運転の依頼例、入力の固定データ（fixtures）、実施結果 |
| `agents/` | Codex など他のエージェント向けの表示設定（`openai.yaml`） |
| `assets/` | 雛形、画像、テーマなど出力に使う素材 |

仕様と実装を両方持つ場合、どちらを正とするかを SKILL.md か仕様側に1文で書く（例: 「`scripts/check.mjs` は `references/spec.md` に合わせる」）。直す側が迷わないようにするため。

## SKILL.md の書き方

### frontmatter

- `name`: ディレクトリ名と一致させる
- `description`: 何をするか、いつ呼び出すかを具体的に書く。呼び出されるかどうかはこの文で決まるため、利用者が実際に使う言い回し（「〜を作って」「〜を直して」）を含める。使わない場面や別スキルへの振り分けもここに書く
- `allowed-tools` など他の項目: 必要な場合だけ追加する

### 本文に置くもの

1. **手順**: ステップごとに、やること・入力・出力を書く
2. **確認する項目と既定値**: 毎回利用者に確認する項目と、既定値で進めてよい項目を分ける。既定値のない項目を推測で埋めない
3. **判断基準**: 分類、優先順位、閾値を表か箇条書きで独立させる。各基準に理由を添える
4. **NG例・OK例**: 過去に実際に起きた失敗を短く対で書く
5. **参照先**: `references/` や他スキルへの案内。どの場面で読むかも書く

SKILL.md を巨大な1枚にしない。手順が複数あるか、詳細が長い場合は `references/` へ分け、SKILL.md を目次にする。

### 判断基準には理由を書く

理由がないとAIは例外に対応できず、後の改修で「冗長だから」と削られやすい。

- 悪い例: 「水曜は予定を入れない」
- 良い例: 「水曜は予定を入れない（集中作業と突発対応のために空けておく）」

不具合や事故を受けて追加したルールには追加した時期と経緯の記録先を添える。削除や簡略化の前にその記録を確認する。

## AIとスクリプトの分担

| 担当 | 例 |
| --- | --- |
| スクリプト | 日付・期間・金額の計算、件数の集計、条件による判定、重複検出、表の整形、形式の検査 |
| AI | 依頼内容の解釈、例外の相談、文面の作成、結果の要約、利用者への提案 |

件数や判定をAIに毎回数え直させない。結果が揺れ、「5件」と書いて4件しか出さないような誤りが起きる。スクリプトが結果を確定し、AIはその結果を読んで文面にする。文面の分岐も、条件と文例を表で決めておけばAIの判断に任せずに済む。

## 外部に出る操作の承認

外部に影響する操作（メール送信、チャットへの投稿、PRの作成、公開、削除）は利用者の承認を得てから実行する。

1. 送信先と送信内容の全文を1回でまとめて提示する。「送ってよいですか？」だけで聞かない
2. 判断が必要な箇所は選択肢で聞く（例: このまま送る / 内容を直す / 利用者が自分で送る）
3. 承認された範囲だけを実行する。承認後に内容を追加したり変えたりしない

出力先によって見せてよい情報が変わる場合、出力先ごとの表記を表で決めておく（例: 本人だけが見る画面には内部の判断材料を出し、社外向けの文面には出さない）。

## テストと試運転

### 回帰テスト

- `scripts/` の判定や除外の条件はテストで固定する
- 実際の利用で見つかった不具合を直す前に、再現するテストを追加する。テストのコメントに不具合の内容を1行で書く
- テストの冒頭に、何を確認するテストかの一覧を置くと、後から抜けが見つけやすい

### 試運転（evals）

手順や判断基準を変えたら、過去の経緯を知らない新しいセッションで試運転する。

- 渡すもの: SKILL.md、該当する `references/`、作業対象への到達方法、依頼文
- 渡さないもの: 前回の失敗、レビュー指摘、今回の改修の意図。渡すと手順書の書き漏れが見つからなくなる
- 試運転では手順どおりに実行させ、各ルールを「適用した / 該当なし / 守れなかった」で自己申告させる
- 合否は呼び出した側が成果物と自己申告を突き合わせて判断する。結果は `evals/` に残す

## 改修の進め方

- 新しいスキルでは時間がかかり頻度も高い作業を1つ選び、短い SKILL.md から始める
- 手直しが多かった箇所から判断基準・NG例・スクリプト・テストを足していく
- 除外ルールや例外の追加は利用者が明示的に合意したものに限る。資料に書いてあるという理由だけで増やさない

## 作成・改修時の確認項目

- [ ] `description` に呼び出す場面と使わない場面が書いてある
- [ ] 毎回確認する項目と既定値で進めてよい項目が分かれている
- [ ] 判断基準に理由が添えてある
- [ ] 答えが一つに決まる処理をAIに任せていない（必要なものは `scripts/` とテストにある）
- [ ] 外部に出る操作に承認の手順がある
- [ ] 同じ手順を他のスキルに書き写していない
- [ ] 手順や判断基準を変えた場合、経緯を知らない新しいセッションで試運転した
- [ ] 共有スキルを追加した場合、Claude Code 側の symlink と README の記載を揃えた
- [ ] `make validate` が通る
