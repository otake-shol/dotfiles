# source-command-verify

変更に対応する合格条件を確認し、必要な検証を実行する。検証依頼だけでコミット・プッシュ・デプロイを開始しない。

## コマンドの選定

- 対象リポジトリの作業ディレクトリと差分を確認し、適用される `AGENTS.md`、README、CI、Makefile、パッケージ設定から検証方法を特定する。
- 明示された必須チェックを優先する。Nodeプロジェクトでは `packageManager` とロックファイルに合わせ、実在するスクリプトを使う。競合があればCIやリポジトリの指示を調べる。根拠なくnpmやグローバルのtscへ切り替えない。
- 設定されていない型チェックやテストを仮定しない。`npx` による暗黙のダウンロードや依存更新を検証に混ぜない。
- コマンドの成功だけでなく、意図したテストが実行されたか、必要な環境依存チェックがスキップされていないかを確認する。

## 編集中の短い検証

変更した挙動を確かめる最小のテストや構文チェックから始める。UIの変更なら必要な描画確認も含める。失敗を修正した後は該当チェックを再実行し、修正の影響範囲に応じて検証を広げる。

dotfilesのOVSなら、リポジトリルートから次のように実行する。

```bash
make design-test DESIGN_TESTS=stow/design/.config/otake/visual-system/test/contrast.test.mjs
```

検査器の判定やそのテストを変更した場合は `make design-mutation` でテストが判定の破損を検出できるかも確認する。通常の資料編集ごとに検査器を改変するテストまで追加しない。

## 完了時の全体検証

- コミット前などリポジトリが指定する節目では必須チェックをすべて実行する。dotfilesでは `make validate` が必須。短い検証の成功で代用しない。
- 修正後の状態で必要なチェックが成功したら終了する。新しい変更・失敗・未解決の懸念がない限り、同じ検証や追加レビューを繰り返さない。
- 同じ失敗に対して修正の根拠が増えない再試行を続けない。コードの失敗と環境の不足を区別し、原因・未検証範囲・再開条件を報告する。必須チェックが未実行なら完了扱いにしない。

## 結果の報告

実行コマンド、対象範囲、成功・失敗・未実行、テスト件数とスキップ理由を簡潔に示す。短い検証だけの場合は全体検証が未実行であることを明記する。終了コード0でも対象0件や必須項目のスキップを合格と呼ばない。
