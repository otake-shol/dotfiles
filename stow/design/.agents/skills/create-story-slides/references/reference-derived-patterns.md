# Reference-derived patterns

Apply these patterns as design and storytelling heuristics. They describe reusable structure, not content: never reuse the slides, names, screenshots, metrics, or claims of a reference deck.

## Stable patterns

### Build pressure before presenting the method

For a case or proposal, establish the sequence below before explaining the solution:

1. Material business, user, or operating stakes.
2. A concrete constraint or contradiction.
3. The gap between the ordinary path and the required outcome.
4. One question that invites the audience to diagnose the bottleneck.
5. A small framework that organizes the answer.

Do not manufacture drama. Each step must be supported by supplied facts.

### Reuse one anchor diagram

Choose a process rail, lifecycle, system boundary, or operating model when the story spans several phases. Reuse it to show:

- the whole problem;
- the current section;
- the intervention point;
- the final before/after result.

Keep the geometry stable. Reorientation cost defeats the purpose of reuse.

Use the right layer for the job: L13 is a primary content-area process visual; N01 from `navigation-components.md` is persistent top navigation that may accompany different primary layouts. They may coexist, but their phase labels, order, and current state must agree.

### Move from abstract structure to concrete behavior

Explain the model first, then show who does what, when, and with which artifact. Useful sequences include:

- operating model -> concrete handoff;
- system view -> affected user flow;
- principle -> real decision;
- process -> annotated evidence;
- `AS-IS -> TO-BE -> decisive difference`.

### Use questions as transitions

Before a framework or recommendation, ask one answerable question. The next slide must answer it directly. Avoid rhetorical questions that only decorate a section turn.

### Pair problems with responses

For each mechanism, preserve a traceable chain:

`Observed problem -> contributing mechanism -> response -> observed effect -> remaining cost or boundary`

Do not relabel an opinion as a measured effect. When the source lacks outcome evidence, end at the response or hypothesis.

### Close through an outcome ladder

When evidence allows, move from the nearest result to the broader implication:

`Output -> process change -> user or operating change -> business result`

Do not skip levels or imply causality that the evidence does not establish.

### Make alignment decks operational

A planning deck should connect:

`Past result -> current context -> governing theme -> priorities -> operating model -> roles -> norms -> commitments`

Acknowledging previous work before introducing new priorities improves continuity. Put detailed staffing and project inventories in the appendix.

## Conditional patterns

- Use serial scenes or illustrated conversations only when actor behavior is the mechanism and the deck has enough time. Compress to `before / after / difference` in short decks.
- Use a full agenda only once. In a long deck, prefer compact section turns or N01 when three or more stable phases require persistent current-position context.
- Use a real artifact as evidence only when authenticity matters. Otherwise rebuild the information in a readable form.
- Use a personal or emotional close only when the presenter owns the message and the audience relationship supports it. A decision deck should end with the decision.
- Use a summary table only when the rows map to distinct commitments, owners, or decisions. Do not repeat prior slide titles as a table.

## Reject these failure modes

- A full spreadsheet, schedule, chat log, code editor, or architecture canvas shrunk below readable size.
- A chart with many series and no highlighted inference.
- A comparison whose axes, criteria, or direction are missing.
- Several feature screenshots presented without a conclusion or selection criterion.
- Body copy, captions, or source labels reduced to document-sized text.
- Titles, notes, or visuals clipped at slide edges.
- Repeated agenda, theme, or summary slides that do not add information.
- Empty section placeholders, drafting prompts, asset-library pages, or template instructions left in the main deck.
- Raw internal URLs, names, avatars, identifiers, metrics, or screenshots copied into a reusable skill or unrelated deck.
- A source deck's management, architecture, or delivery choice promoted to a universal best practice without validating its conditions.

## Source boundary

Use reference decks to learn sequence, hierarchy, pacing, comparison, evidence handling, and layout behavior. Do not copy branded visual identity, confidential content, or unsupported domain conclusions. When the user asks to match a specific reference more closely, obtain explicit authorization for any source-specific content or assets and retain traceable citations.
