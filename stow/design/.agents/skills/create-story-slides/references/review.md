# スライドの検証と発表準備

新規制作、既存デッキの編集、レビュー依頼で共通に使う。
レビューだけの依頼では原稿を変更せず、ページ番号、問題、修正案を報告する。
構成・自己紹介・レイアウトの判断は [スキル本体](../SKILL.md) と各参照仕様を正本とする。

## 機械検査

テーマと出力形式は [marp-output.md](marp-output.md) で解決する。
新規StandardデッキのPDF生成には `scripts/build.sh` を使う。内部で
`ovs deck verify`（静的lint＋描画check）を実行するため、同じ検査を別に繰り返さない。
持ち時間が指定された場合はビルド前に `ovs deck lint slide.md --mode present --minutes N`
を実行する。ビルドは時間指定を受け取らないため、この検査で9割超の警告を確認する。
時間だけを見直す場合は静的検査だけを再実行し、描画検査を繰り返さない。
レビュー、HTML出力、既存テーマのデッキでは次を使う。

```bash
# slide_themeには実際のデッキで使うCSSを指定
ovs deck outline slide.md --minutes 10
ovs deck verify slide.md --theme "$slide_theme" --mode present --minutes 10 --shots /tmp/slide-check
ovs deck rules
```

配布資料には `--mode read` を使う。時間指定がなければ `--minutes` を省く。
`ovs` がなければ `node "${XDG_CONFIG_HOME:-$HOME/.config}/otake/visual-system/scripts/ovs.mjs"`
を確認する。どちらも使えなければMarpの画像出力で目視確認し、機械検査を未実施と報告する。

- errorは修正する。warnも原則修正し、指定テンプレートや正本仕様に沿って残す場合は理由を記録する。
- 検査の目安に合わせるためだけに既存ブランド、自己紹介、資料の目的を変更しない。
- あふれは文章の整理、レイアウト変更、分割の順に検討する。文字の一律縮小で済ませない。
- 修正後は該当する検査を再実行し、新しい画像で確認する。

## 目視検査

[媒体共通レビュー](../../../design/design-intent.md) の完成物の確認と、
[design-system.md](design-system.md) のQAを適用する。

1. `contact-sheet.png` の25%一覧で話の流れ、型の偏り、密度の緩急を確認する。
2. 全ページの `slide-NN.png` を開き、指摘箇所、文字の切れ・重なり、出典、画像、フォントを確認する。
3. ノートを見ず、実際の掲載・投影サイズで中心メッセージを読み取れるか確かめる。
   発表用では3秒で要点をつかめるかを目安にする。配布用では本文だけで理解できるかを確認する。
4. 主張を実データ・図・実画面が支え、見せたい領域が読めるかを確認する。
   生成成功や図解素材だけのlint成功をデッキ全体の合格と扱わない。

## 完成条件

- 読めない文字、はみ出し、未置換のプレースホルダー、画像欠落がない。
- 外部の主張や数値に追跡可能な出典があり、未確認の効果を断言していない。
- 中心メッセージを証拠が支え、本文に無関係な詳細が詰め込まれていない。
- 自己紹介の判定はスキル本体に従い、公開範囲を守っている。
- 新規Standardの発表用ではL12に結論・次の行動、続くL18に新情報を含まない終了表現を置く。
  既存デッキにはL18を強制追加せず、現在の締め方が目的を満たすかを確認する。
- 未確認の検査を合格とせず、成果物と残る制約を分けて報告する。

## 発表準備と報告

- 発表用ではノートを台本として読み、持ち時間の9割を目安に収める。
  `ovs deck outline` の推定と声に出した実測を区別する。超過は内容を整理して直す。
- 意思決定の資料には想定質問の補足を付録に用意する。
- 成果物、自己紹介の判定、検査結果、目視したページ、残したwarnの理由を報告する。
- レビュー依頼では重大な問題から並べ、推定と実測、見た目の好みと利用上の不具合を区別する。
- 発表後の改善依頼では実時間、詰まった説明、質問、反応を整理する。
  繰り返す問題を指針へ反映するときは [sources.md](sources.md) に従う。
