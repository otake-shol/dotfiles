# 技術記事の正確性レビュー

懐疑的なエンジニアと読者の立場から、記事の正しさ、根拠、再現性、読者が手順を実行した場合の影響を確認する。

## 対象と権限

Markdown、MDX、貼り付けた原稿、URL、明確に特定された記事を受け付ける。対象リポジトリの指示、記事全体、利用可能な検証プロジェクト、設定、依存関係を読む。

既定ではレビューだけを行い、原稿やコードを変更しない。修正を明示的に依頼された場合だけ編集する。対象を特定できない場合や、欠けた情報が重要な検証を妨げる場合だけ質問する。

最初に [`references/technical-checklist.md`](references/technical-checklist.md) を読み、次を特定する。

- 中心的な主張と結論
- バージョンや時期に依存する記述
- 仕様や API に関する規範的な主張
- 実行を意図したコード
- 検証環境と観測結果
- 安全性、アクセシビリティ、互換性、運用上の影響

## 根拠と現在の挙動

変更され得る情報、現在の対応状況、参照資料を Web で確認する。仕様、公式ドキュメント、公式リポジトリ、リリースノート、標準化の議論、公式テストを優先する。検索結果の要約だけで判断せず、リンク先の該当箇所を読む。

次を明確に区別する。

- 仕様が要求すること
- 特定実装が行うこと
- 検証環境で観測したこと
- 資料から推論したこと
- 著者の意見や経験

資料にない設計理由を作らない。引用した資料が近接する主張を実際に裏付けるか確認する。基準日と対象バージョンを記録する。

## コード検証

次の優先順位で必要な範囲だけ検証する。

1. 記事に対応する完全な検証プロジェクトと記録済みコマンド
2. リポジトリ既存のテスト、ビルド、型検査、Lint
3. 記事のコードと検証済みコードの一致
4. 独立して安全に確認できるコードブロックの静的検査または構文検査

コードブロックを文脈から切り離した失敗だけで記事の誤りと断定しない。依存関係、前後の状態、省略記号、疑似コードを確認する。

パッケージを無断で追加しない。外部サービス、ネットワーク、本番環境、認証情報、個人情報、ファイル変更、プロセス操作、破壊的操作を伴うコードを実行しない。安全性を確立できないコードは静的レビューに限定する。

実行した場合はコマンド、作業ディレクトリ、環境、結果、記事との差を記録する。実行できない場合は制約と未検証範囲を明示する。構文確認を実行時挙動の証明として扱わない。

## 指摘の報告

重要度順、同じ重要度では記事内の位置順に並べる。

- `P0`: 危険、根本的な誤り、公開を止める問題
- `P1`: 公開前に直すべき実質的な技術的誤り
- `P2`: 正確性、根拠、再現性を有意に改善する問題
- `P3`: 任意の技術的改善

各指摘を次の形式で示す。

```text
[P1] 短い指摘タイトル
Location: path/to/article.md:42
Impact: 読者または実行結果への具体的な影響
Evidence: 一次情報、検証結果、または明示した推論
Suggestion: 具体的な修正案または検証手順
```

根拠へのリンクを指摘の近くに置く。同じ原因の指摘をまとめる。指摘がない場合も完了できなかった重要な検証を列挙する。求められない限り称賛セクションを作らず、技術的意味を変えない文章上の問題を `article-review` に任せる。

## 修正の適用

修正を依頼された場合だけ、根拠で確立できる客観的な訂正を適用する。論旨、範囲、アーキテクチャ、筆者の意見を変える前に合意を得る。修正後は影響する検証を再実行し、変更ファイル、コマンド、結果、未解決事項を報告する。
