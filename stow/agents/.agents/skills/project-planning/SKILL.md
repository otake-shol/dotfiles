# プロジェクト計画

計画の内容と説明用の資料をつなぐ。計画の正本を明示し、スライドにはその要約を使う。

## 計画の作成・更新

- 対象リポジトリの指示と既存の計画・課題・提供資料を読む。既存の計画書を優先し、会話にない共有リポジトリや接続を推測しない。
- Planbaseの `*.project-plan.json`、Project Portfolio Sheets、GitHub Issue・Projectなど既存の正本がある場合はその項目・ID・更新規約を確認して利用する。別形式の計画を新たな正本として増やさず、説明用の要約には元の参照先を残す。
- 目的、対象期間、読者、欲しい成果物を依頼から判断する。範囲・期限・完了条件が大きく変わる不明点を質問し、それ以外は仮定を明記して草稿を進める。
- [計画の雛形](references/project-plan.md)を読み、案件に必要な項目で計画を作る。小さな案件には不要な表を増やさない。新規案件に過去の振り返りを強制しない。
- 完了条件を観察できる成果にする。作業を成果物に分解し、優先順位の理由と対象外を示す。日程には依存関係と実行可能な体制を反映する。
- 全体計画の1枚絵やL0・L1・L2を作る・見直す場合は [スケジュール階層](references/schedule-levels.md)を読む。L0の全体合意、L1の工程管理、L2の実行を親IDと出典でつなぎ、基準日程と現在の予測・実績を区別する。
- L0では関係者台帳の全員と主要マイルストーンを図に対応づけ、各人の関与期間・受け渡し・判断を示す。役割の配置例を実際の人数と誤認せず、関係者ID・成果物ID・マイルストーンIDを区別する。
- L1・L2をスプレッドシートへ表現する場合は [既存Sheets雛形への対応](references/sheets-schedule.md)を読む。Project Portfolio Sheetsの既存Single版を優先し、WBSを共通の入力元として工程と詳細作業を親IDでつなぐ。既存の数式・入力規則を確認し、概要表示の範囲と予測日程の不足を明示する。
- 確認済みの事実、提案・仮定、未決事項を区別する。根拠のない工数、KPI、日付、予算、担当者を確定値として埋めない。未決事項には判断者と確認点を付け、判断者も不明なら未定とする。
- 計画ファイルを依頼された場合は対象プロジェクトの規約に従って保存する。規約がなければ `docs/plans/YYYY-MM-DD-<slug>.md` を候補にする。共通スキル内に入力済み計画を保存しない。
- 更新時は現行の計画・課題と照合し、変更理由、影響する完了条件・日程・担当、次の確認点を残す。資料間の矛盾を黙って解消しない。

## スライドへの展開

スライドやPDFを依頼された場合にだけ制作へ進む。

汎用の計画資料を新しく作る場合はdotfilesの `templates/project-plan-slides/README.md` と `deck.md` を雛形として利用できる。目的・範囲・実行条件・判断・運用をつなぐ構成を案件に合わせて調整し、入力済みの資料は対象プロジェクトに保存する。既存の雛形やユーザー指定の形式を優先する。

- 利用可能な `create-story-slides` の `SKILL.md` を読み、その参照資料・出力・描画検証の手順を使う。dotfilesでは `stow/design/.agents/skills/create-story-slides/`、配置後は `~/.agents/skills/create-story-slides/` を参照できる。見つからなければ構成案まで作り、利用できない工程を伝える。
- team-playbookの `planning-toolkit` など既存の計画資料を更新する依頼ではそのテンプレート・出力手順を確認して継続する。既存形式を使う依頼から新しいスライドシステムへの移行を推測しない。
- 優先順位・役割・実行方法の合意が目的なら計画モード、承認や選択が目的なら提案モードを選ぶ。ユーザー指定の形式・テンプレートを優先し、OVS指定時は `source-command-slides`、編集可能なPowerPointや既存Google Slidesなら対応する専用スキルを使う。
- 目的・完了条件・範囲・主要成果物・依存関係・責任・リスク・次の判断を物語にする。全項目を1枚ずつ機械的にスライド化せず、詳細な作業表は必要に応じて付録に置く。
- 計画の正本と版・確認日を制作時の参照情報に残す。未決の担当・期限や仮定を確定した約束に書き換えない。計画に変更が必要なら理由を示し、正本への反映を依頼の範囲で扱う。

## 完了確認

読者が「何を、誰が、どの条件で完了し、次にいつ何を確認するか」を把握できることを確認する。担当や日程が未決なら、その確定に必要な判断が残っていれば草稿として渡せる。成果物の参照先、残る未決事項、実際に行った検証を短く報告する。

計画・資料の依頼から、チケット作成、他者への送信、公開、定期実行の設定までを自動的に広げない。
