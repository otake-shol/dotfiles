# 媒体別の実行手順

## トークン効率を考慮した分担

003以降も1セットずつ進める。既存素材の有無を先に確認し、必要な制作だけを依頼する。

|担当|起動時の指定|対象|
|---|---|---|
|制作|Sol / medium|対象1セットの短尺台本・図解指定・媒体別投稿文・長尺公開文言。新しい長尺や複雑な条件では必要に応じてhighへ変更|
|独立レビュー|Astra / high|初回は原典・計算・適用条件・理解確認。修正後は指摘箇所と影響範囲、最終版の代表画像|
|進行・検査|メイン＋ローカルスクリプト|既存素材調査、参照版照合、音声・映像生成、尺・フォント・非無音検査、確認ページ生成|

起動時は会話全文を渡さず、科目・問題ID、対象原典、参照版、必要な品質基準、出力形式、書き込み先を渡す。台本・原典を1つの対象別資料へまとめ、制作担当は成果物ファイルと短い完了報告を返す。独立レビューでは原典も参照し、制作担当の検算結果だけを信頼しない。

単純なコピー、数値の再計算、API実行、生成待ちに別のモデル担当を追加しない。重い生成は逐次実行し、待ち時間には公開用文言や検証記録を進める。全編生成前に台本の指摘を解消し、音声の読み・実尺を点検する。修正後は音声・画面の既存キャッシュを利用する。

使用可能なモデル名はセッションのツール定義で確認する。起動時に指定したモデル、担当数、修正往復、全編生成回数を記録する。実行IDやトークン実測を取得できなければ未取得とし、節約率を断定しない。モデル変更で入力トークン数自体が減るとは限らない。

サブエージェントの追加でトークン使用量が増える場合もあるため、担当を増やすこと自体を削減策にしない。[OpenAI公式のマルチエージェント説明](https://developers.openai.com/api/docs/guides/responses-multi-agent)を参照（2026-09-25確認）。

## 長尺と原典

`plans/curriculum/curriculum.json`の対象問、関連論点、基礎編候補、補足条件を読む。カリキュラムは編集計画なので、完成動画の原本・最新ジョブ・教材版を別途確認する。

catchup-studioが動いていれば制作一覧と既存セットを使う。同じ入力の再取り込みは既存企画へ戻し、原典更新時は候補として扱う。台本の手編集を上書きしない。生成状況を戻すときは`origin.output_id`だけでなくepisode ID・版を確認する。基礎編と問題解説が同じoutput IDを持つ例がある。

長尺では原問の全条件・選択肢と解答理由を照合する。共有の基礎編に今回不要な範囲があっても複製せず、必要範囲への案内や補足の要否を判断する。002は`foundation-cvp`が候補で、既存episodeの末尾は071。対象問ごとの適用確認後に再利用する。

## 図解アニメーションの制作

2026-10-02に基礎編005のRemotion組み込み比較版を本人が選択した。数値・条件・字幕を残し、説明に合わせて矢印と式を動かす演出を今後の制作・再編集の方針にする。全編の試聴、学習効果、公開承認をこの選択で代替しない。

- 数式の展開、資金の流れ、時点の換算、グラフの変化を説明する場面でRemotionを優先検討する。既存の静止画や制作エンジンを一律に置き換えず、必要な場面へ補助的に組み込む。
- 原本のline IDと固定ジョブのtimelineから表示区間を決める。音声の実尺に同期させ、試作の固定フレーム数・数値・パスを別教材へ流用しない。問いの正答を解説前に表示しない。
- 配色・フォント・字幕・キャラクターの領域を既存チャンネルへ合わせる。矢印の向きと式の操作を説明へ対応付け、数値、単位、期間、適用条件を表示する。掛け合いでは実話者と発話を保持する。
- 図解だけの変更では元の音声とBGMを保持する。差し替え後に字幕の同期、前後の接続、黒い角・文字欠け・重なり、非無音・全編デコードを確認する。音声をコピーした場合はストリームのハッシュ一致も検査する。
- 再生成できるソースと依存関係、入力episode版・job ID・動画ハッシュ、対象line ID、差し替え区間、出力先を記録する。合成後の動画が既存ジョブと別なら比較版として明記し、既存の公開状態や生成済み判定を更新したことにしない。

制作リポジトリの`output/remotion-integration-005-20261002/INTEGRATION.md`に採用例がある。`integration.tsx`と`integrate.mjs`はこのPC向けの試作で、制作エンジンの標準機能ではない。基礎編005では「121万円÷1.10＝110万円」を使い、当初の支出100万円と区別した。出力がなくても上記の方針から制作できるよう、参照先の存在を着手時に確認する。

## 短尺とX

制作画面の短尺／Xフォーム、または既存のローカルAPIを使う。APIを使う場合は現在の`server.mjs`と`social.mjs`を確認し、書き込み時は`/api/session`から得たトークンとOriginを送る。トークンをログや成果物へ出さない。

| 操作 | 既存APIと入力 |
| --- | --- |
| 短尺の作成 | `POST /api/episodes/:source/short`。現在の`revision`、根拠`lineIds`最大12、title、hook/explanation/conclusionのtext/headline/sub |
| 台本の保存 | `PUT /api/episodes/:id`。取得した現在のrevisionとepisode。origin/derivationは保持 |
| X投稿の保存 | `PUT /api/episodes/:id/x`。Xの現在revision、sourceRevision、draft（text/card/lineIds） |
| 生成 | `POST /api/jobs`。episodeId、revision、mode。Xはmode=xでX下書きのrevisionを使う |
| 状態確認 | `GET /api/jobs`と`GET /api/episodes/:id`。今回のジョブIDで追跡する |

短尺フォームの3場面は初期ひな形。必要なら独立episode内でセリフ・画面を分ける。各字幕72文字以内、portraitの画面制約、90秒上限を検査する。横動画の挨拶・目次を持ち込まない。基礎編から作る場合は横用`dialogue_speakers`や`corner_sections`を除き、縦画面の`visible_sections`と実話者をそろえる。

縦動画は720×1280・30fps。文字の描画幅は文字数検査だけで保証されないため、prepareで確認する。生成前にNemoの読みを確認し、生成後は数字・単位の途中改行、句読点の孤立、字の欠け、Qとトイの取り違えを最終フレームで確認する。

Xは今回使う数値例が含まれる短尺から派生させると参照関係を保ちやすい。`xDraft`で本文と画面上限を検査し、mode=xで図を生成する。001では補足文が文字数内でも画像幅を超えたため、条件を保って短くした。数学的意味が同じことを再確認する。X動画投稿が依頼された場合は既存縦MP4の利用可否を確認して文面を追加し、新規レンダリングを既定にしない。

## 媒体別の確認ページ

001の`channels/demo/publication/set-001/`を形式の実例として読む。番号・episode/job ID・題名・説明・例題・章・根拠行は対象に合わせて執筆する。値をそのまま次の番号へ置換しない。

- `draft.json`：長尺ごとの固定job ID・raw episode revision、タイトル候補、概要欄、章のline ID、サムネイル構成。条件・出典・CTAを今回の題材へ合わせる。
- `set.json`：短尺とXの固定episode/job ID・revision。短尺はepisodeのSHA、Xはx-post.jsonのSHA。
- `output/`：再生成可能な派生物。編集原本や公開結果の保存先にしない。

```bash
# video-repoのルートで実行。例は財務・会計002
node scripts/publication-draft.mjs channels/demo channels/demo/publication/set-002/draft.json --check
node scripts/publication-set.mjs channels/demo channels/demo/publication/set-002
```

現行の`publication-set.mjs`は長尺＋短尺1本＋その短尺由来のX1件を集約する。依頼が長尺だけなら`publication-draft.mjs`で完了できる。不足する媒体をダミーで埋めてページを通さない。他科目は`set-economics-002`のように科目を含めて番号衝突を避ける。

音声クレジットは固定ジョブのaudio-contextと実際の話者から抽出する。現在の集約スクリプトはNemo前提で検査するため、他エンジンへ変えた場合はその処理を先に確認する。公開URL未確定時は架空のURLやローカルURLを投稿文に混ぜない。YouTube/TikTokなどの要件や素材利用条件を判断する際は最新の公式資料を確認する。

## 検証と引き渡し

コードを変えたらリポジトリ指定の`npm run verify`を実行する。内容だけなら原典・検算・フォント・画像・音声・参照版を対象に絞って検査する。表示変更ではprepareまたはallで実画面を確認する。同一入力の再実行で既存の手編集が残ること、参照版が変われば不一致を検出することを確認する。

再生、投稿文コピー、ダウンロード、PCとスマホ幅を確認する。レビュー記録へ「機械検査済み」「AI編集評価済み」「本人試聴待ち」「公開未承認」を実態に応じて記す。公開用ZIPのreview/package APIは本人確認を代行するために呼ばない。ローカル素材作成は完了まで進める。

## 作業票の記録項目

`channels/<channel>/reviews/<科目-番号>/work.md`等へ、既存の同種記録を優先して保存する。

1. 対象問ID、今回依頼された範囲、到達目標、原典と参照版
2. 既存成果物と基礎編の再利用範囲・不足条件
3. 各出力のepisode ID、revision、job ID、機械検査・AI評価・本人確認・公開の別々の状態
4. 採用した例の検算、定義・主張・画面・根拠line IDの対応
5. 指摘、修正、最終版での再確認、未確認事項
6. 制作担当とレビュー担当、修正往復、全編生成回数、取得できる消費量（取得不可は未計測）
7. 次に実行する具体的な操作と必要ファイル。判断理由と原本の所在を残し、全文台本を作業票へ複製しない

作業票の状態は前回終了時点の記録。再開時はinspect-setと原本で更新する。未実行の工程を完了扱いにしない。
