# L0・L1・L2のスケジュール管理

全体の合意、工程の管理、日々の実行を同じ計画の異なる粒度として扱う。ここでのL0・L1・L2は [team-playbookの階層管理ガイド](https://github.com/otake-shol/team-playbook/blob/main/pm-templates/schedule/schedule-guide.md)に合わせた運用上の呼び方。組織によって名称・レベル番号が異なるため、既存の定義を優先する。PMBOKの必須帳票や一律のレベル定義として扱わない。

## 階層と対象者

| 階層 | 名称・目的 | 主な読者 | 粒度の目安 | 成果物 |
| --- | --- | --- | --- | --- |
| L0 | グランドスケジュール。全体の方向性・期限・主要判断の合意 | スポンサー、経営層、主要関係者 | 月〜四半期。短期案件では週などへ調整 | 時間軸付きの全体計画1枚 |
| L1 | マスタースケジュール。工程と依存関係の管理 | PM、PO、チーム責任者 | 週〜月、工程・主要成果物単位 | 工程表、主要成果物、マイルストーン、依存関係 |
| L2 | 詳細スケジュール。担当者が実行する作業の管理 | 実行担当者、開発チーム | 日〜週、作業単位 | 作業一覧、チケット、詳細ガント |

数字をWBSの階層深さと機械的に一致させない。WBSは成果物・作業を分解する構造で、スケジュールには順序・期間・担当・稼働条件も必要。

## L0の1枚絵

- 横軸: プロジェクト全期間。月・四半期など同じ長さの区間で表示する。
- 縦軸: 今回のL0では関係者全員を氏名・役割とともに配置する。実行担当だけでなく、意思決定者、依頼者・利用者、レビュー担当、外部協力者、移管先など案件に登場する人を関係者台帳から照合する。
- 期間: 各工程の開始・終了をバーで示し、幅を時間軸へ合わせる。
- 判断: 主要な成果物の受け渡し、合意、承認、受入、公開、移管などをマイルストーンで示す。同じマイルストーンIDを共通時間軸と各人の行で共有し、誰が準備・確認・判断・受領するかを対応づける。
- 依存: 全体の期限や着手を左右する関係だけを表示し、詳細はL1へ置く。
- 前提: 全体期限、主要な稼働・外部依存、必要な判断を短く添える。
- 出典: 元の計画、版・確認日、計画案か合意済みかを明示する。

個別タスクを縮小して1枚へ詰め込まない。L0だけで「いつ何ができ、どこで判断し、何が遅れると全体に響くか」を読める状態にする。

## 全員の関与とマイルストーン

6行・6つの節目はスライド上の配置例で、人数や節目の上限ではない。実際の全関係者と主要マイルストーンを先に台帳へ列挙してから図へ配置する。関与しない期間は空白にし、全員が全節目へ参加するように見せない。

| 関係者ID | 氏名・所属 | 役割 | 関与期間・工程 | 関与するマイルストーンIDと行動 |
| --- | --- | --- | --- | --- |
| | | | | |

| マイルストーンID | 名称・日付 | 成果物・完了条件 | 実行・準備者ID | 確認者ID | 最終判断者ID | 受領者ID | 後続工程・期限への影響 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| | | | | | | | |

図のバーで各人の主要な関与期間、菱形で節目への参加・判断、矢印で成果物の受け渡しを示す。菱形だけで最終承認者とは断定せず、台帳と役割説明で区別する。予測日と合意済みの日付も正本で分ける。

共通スライド雛形の依存矢印には経路Dを使う。菱形の右側から水平に伸ばし、工程中の確認点を表す白丸の真上で垂直に下ろす。白丸には名称・時期・条件・担当・証拠を正本で対応づける。工程全体の開始条件を示す矢印とは区別し、実計画にない確認点や依存を作らない。線の長さや曲がりを期間・待ち時間として扱わず、バーや文字と交差する場合は経路を調整する。

同じチームの行へまとめる場合も全員の氏名を明示し、各人の関与を追えるようにする。役割名だけで全員を表現したことにしない。人数が多い場合は全員を載せた大きな1枚絵を用意し、スライドにはその読みやすい表示を使う。文字を縮小して人数を収めたり、説明なく関係者を省略したりしない。未定の役割には「担当未定」と確定に必要な判断を記載する。

主要成果物ID（P1等）、関係者ID（R1等）、マイルストーンID（M1等）を分ける。L1の親IDは主要成果物を参照し、人物を工程の親として扱わない。

## L1の管理項目

工程・主要成果物ごとにID、親となるL0項目、完了条件、開始・終了、責任者、先行ID、マイルストーンを持つ。外部依存には回答期限・確認先を記録する。工程を完了とする基準を主要成果物の検証と対応づける。

| ID | L0親ID | 工程・成果物 | 完了条件 | 基準開始・終了 | 現在の予測開始・終了 | 責任者 | 先行ID・外部依存 | 判断点 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | | | | | | | | |

## L2の実行項目

作業ごとにID、L1親ID、成果物・完了条件、担当、見積もり、開始・終了、先行ID、状態、阻害要因を持つ。単なる「対応済み」で完了にせず、レビュー結果や成果物など確認できる証拠を残す。

| ID | L1親ID | 作業・成果物 | 完了条件・証拠 | 担当 | 見積もりと単位 | 基準開始・終了 | 現在の予測開始・終了 | 実績開始・終了 | 先行ID | 状態・阻害要因 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | | | | | | | | | | |

詳細表は正本側で扱い、スライドでは代表的な作業と親子関係を見せる。

スプレッドシートでは [既存Sheets雛形への対応](sheets-schedule.md)を使い、Single版のWBSをL1・L2の共通入力元にする。概要スケジュールの抽出範囲、ガントの基準・実績表示、予測日程の制約を確認する。

## 正本と階層間の連動

各階層の保存先・更新担当・確認頻度を決める。同じツールを全階層の正本にしてもよい。別ツールの場合はIDと参照先でつなぎ、同じ項目を独立して二重入力しない。

| 階層 | 正本の場所 | 更新担当 | 確認頻度・契機 | 上位へ共有する条件 |
| --- | --- | --- | --- | --- |
| L0 | | | 全体レビュー・重要な変更時 | スポンサー判断が必要な変更 |
| L1 | | | 定期レビュー・主要な予測変更時 | 全体期限・主要成果物・体制への影響 |
| L2 | | | 日次等の実行状況確認時 | 先行条件・完了条件・工程期限への影響 |

- 上から下: L0の成果・期限・判断条件をL1へ分解し、L1の成果物を実行可能なL2へ分解する。各項目を親IDへ結びつける。
- 下から上: L2の実績・予測・阻害要因からL1への影響を確認し、主要期限・成果・外部依存に影響する場合はL0の判断へつなぐ。
- 工程期間: 並行作業の所要時間を単純に足さない。作業の順序、休日、担当の稼働制約、外部依存から現在の予測を判断する。
- 変更: 合意済みの基準日程と現在の予測・実績を分ける。予測が変わっても基準を黙って上書きしない。変更理由、影響、判断者、決定状態を残す。
- 未決: 仮置きの日程・担当を確約として集約しない。必要な回答と判断期限を明示する。
- 将来: 近い期間をL2まで具体化し、遠い期間はL0・L1で保つ。詳細化の確認点を決める。

## スライドとの対応

計画スライドの9枚目にL0の時間軸付き全体図、10枚目にL1の管理例、11枚目にL2の代表作業を配置する。10・11枚目は正本の一部を説明する要約で、詳細な台帳をスライドへ移さない。

スケジュールを階層化しただけではPMBOKの全要素を満たしたことにはならない。品質、価値、財務、関係者への情報共有等の計画も案件に応じて確認する。
